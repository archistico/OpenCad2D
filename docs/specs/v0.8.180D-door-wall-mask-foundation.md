# Specification — v0.8.180D Door Wall-Mask Foundation

## Purpose

This slice adds the first non-destructive wall-opening mask to `DoorEntity`. The goal is to let a parametric door visually hide the wall linework below its opening without trimming, splitting or otherwise modifying existing wall entities.

The implementation follows `docs/specs/shared-wall-mask-openings.md`: masking is an entity-owned visual/export behavior, not a destructive edit command.

## Implemented scope

`DoorEntity` now has a persistent `MaskWallOpening` boolean property. The default is `true` for new doors so that architectural insertion gives the expected opening behavior immediately. Existing/legacy JSON that does not contain this property also deserializes to `true` through the DTO default.

Generated door geometry now exposes an optional `WallMaskPolygon`. For the first version this polygon is the door opening footprint:

```text
local (0, -wallThickness/2)
local (width, -wallThickness/2)
local (width,  wallThickness/2)
local (0,  wallThickness/2)
```

The polygon is transformed through the same insertion point, local axes and 9-point anchor rule used by the visible door linework. The anchor is still resolved against the wall-opening footprint, not against the swing arc.

## Rendering and export behavior

The mask is drawn before the visible door symbol and after whatever entities were rendered earlier according to normal draw order. In ordinary use, wall lines are created first and the door is inserted later, so the mask covers the wall opening and the visible door linework is redrawn above the mask.

| Target | Behavior |
|---|---|
| Canvas | fills the mask polygon with the CAD canvas background color, then draws the door linework. |
| SVG | writes a white `<polygon>` before the generated door `<line>` elements. |
| PDF | writes a white filled polygon before the generated door linework. |
| DXF | writes a white `SOLID` `HATCH` before the generated door `LINE` entities. |
| JSON | persists `MaskWallOpening`. |

The DXF/PDF/SVG mask is deliberately a white wipeout-style shape. It is not a real boolean subtraction and does not change the wall entities.

## Command workflow

`DOOR` keeps the first-pass insertion behavior from v0.8.180C and adds a mask toggle option:

```text
M = Mask
```

The option toggles the current door-tool default for subsequent insertion. New `DoorTool` instances start with mask enabled. The current behavior remains single-click insertion with preview; width, wall thickness and opening angle are still fixed defaults until later HUD parameter-editing slices.

## Property Panel

The selected door now exposes:

```text
Wall mask: Yes/No
```

Changing this value replaces the door entity through the normal undoable property-panel command path. Undo restores the previous value.

## Explicitly out of scope

This slice does not implement:

- real trimming/splitting of wall entities;
- automatic wall detection;
- automatic wall-thickness detection;
- draw-order management commands specific to door masks;
- transparent/custom-color masks;
- mask support for windows, which belongs to the first `WindowEntity` slice;
- width/thickness/opening-angle HUD editing.

## Known first-version limitations

The mask only hides geometry drawn before the door according to draw order. If a wall entity is moved above the door draw order, it can appear on top of the mask. This is acceptable for the first non-destructive implementation and should be documented as a draw-order rule rather than solved by destructive geometry edits.

SVG/PDF/DXF exports use a white wipeout shape. This is appropriate for normal paper-style output. Transparent-background SVG workflows may show the white mask polygon; a true transparent clipping/wipeout mechanism is deferred.
