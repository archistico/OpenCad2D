# Specification — v0.8.110 Blocks

## Purpose

Introduce reusable block definitions and block references.

Blocks are a foundational CAD concept. They allow repeated symbols, details, title blocks and components to be inserted many times while sharing a single definition.

## Core concepts

### BlockDefinition

A block definition is stored in the document and contains local geometry.

Suggested fields:

```text
Id
Name
BasePoint
Entities
CreatedAt/UpdatedAt optional metadata
```

The entities inside a definition are defined in block-local coordinates.

### BlockReferenceEntity

A block reference is an entity in the drawing that points to a definition.

Suggested fields:

```text
Id
LayerId
BlockDefinitionId
InsertionPoint
ScaleX
ScaleY
RotationRadians
IsMirrored optional/deferred
```

The reference does not duplicate the definition geometry.

## Document model

Suggested shape:

```text
Document
├─ Entities
│  ├─ LineEntity
│  ├─ CircleEntity
│  └─ BlockReferenceEntity
└─ BlockDefinitions
   ├─ Door_80
   ├─ NorthArrow_A
   └─ TitleBlock_A3
```

## Initial behavior

A block reference should behave as a single selectable entity.

Supported operations:

- render;
- hit test;
- select;
- move;
- copy;
- rotate;
- scale;
- mirror if transforms support it cleanly;
- snap to transformed geometry inside the block;
- save/load.

## Rendering

Rendering algorithm:

1. Find the referenced `BlockDefinition`.
2. Build the reference transform from insertion point, rotation and scale.
3. Render each definition entity through that transform.
4. Apply current viewport transform after world-space conversion.

Selection highlight can initially draw a transformed bounding box around the block reference.

## Hit testing

Initial policy:

- Treat the block as one entity.
- Hit testing checks transformed child geometry.
- If any child geometry is hit, the block reference is selected.

Deferred:

- Selecting nested child entities directly.
- In-place block sub-selection.

## Snapping

Initial policy:

- Block references expose snaps from transformed child geometry.
- Endpoint, midpoint, center and nearest snaps should work where child entities support them.
- Snap result should still target the block reference entity, unless the snap API already supports child metadata.

## Persistence

Native JSON must persist:

- block definitions;
- entities inside definitions;
- block references;
- reference transform values.

Round-trip requirements:

- Definition IDs remain stable.
- Reference IDs remain stable.
- Multiple references to one definition still point to the same definition after reload.

## Commands and tools

### Create Block

Workflow:

1. User selects entities.
2. User runs `Create Block`.
3. User enters block name.
4. User picks base point or accepts default base point.
5. Application creates a block definition.
6. Application replaces selection with a block reference, or asks whether to keep original entities.

Recommended first behavior:

- Replace selection with a reference.
- Support undo as one operation.

### Insert Block

Workflow:

1. User runs `Insert Block`.
2. User chooses a definition from a small dialog/list.
3. User picks insertion point.
4. Optional later: scale and rotation prompts.

### Edit Block

Recommended first implementation:

- isolated editor mode/window;
- user edits block-local entities;
- save/apply updates definition;
- all references update automatically.

Avoid in-place editing in v0.8.110 because it requires inverse transforms, context display, nested selection and more complex command routing.

### Explode Block

Workflow:

1. User selects a block reference.
2. User runs `Explode`.
3. Application creates transformed copies of definition entities in world coordinates.
4. Application removes the block reference.

## Block Manager

Implemented minimal manager:

- list block definitions;
- show name, definition entity count, instance count and approximate bounds;
- rename block definitions with duplicate/empty name validation;
- delete unused block definitions only;
- block deletion is rejected while references still exist in the drawing;
- insert selected block with default scale `1` and rotation `0`, then pick insertion point on the canvas;
- block definition changes are applied through an undoable command.

Deferred:

- thumbnail previews;
- nested block tree;
- attribute editor;
- purge command.

## Testing checklist

Core tests:

- document can contain block definitions;
- block reference resolves a definition;
- multiple references share one definition;
- transformed bounds are correct;
- move/rotate/scale modifies reference transform, not definition geometry;
- explode produces correct world-space geometry.

Persistence tests:

- block definition round-trip;
- block reference round-trip;
- multiple references preserve shared definition ID;
- missing definition is handled as invalid/recoverable data.

Interaction tests:

- hit test block reference;
- snap to transformed child line endpoint;
- snap to transformed child circle center;
- create block from selected entities;
- insert block creates reference;
- edit definition updates all references.

## Accepted first-version limitations

- No block attributes.
- No dynamic parameters.
- No in-place editing.
- No nested blocks unless they fall out naturally and safely from the model.
- No per-reference layer override beyond the reference entity layer.
- No external block libraries yet.

## Implementation checkpoint — v0.8.110 foundation

The first implementation checkpoint introduces the data model required for blocks without trying to solve the whole block workflow at once.

### Added concepts

```text
CadDocument
├─ BlockDefinitions
│  └─ BlockDefinition
│     ├─ Id
│     ├─ Name
│     └─ Entities in local block coordinates
└─ Entities
   └─ BlockReferenceEntity
      ├─ BlockDefinitionId
      ├─ insertion point
      ├─ X axis vector
      ├─ Y axis vector
      └─ cached definition bounds
```

### Current behavior

- Block definitions are persisted in `.opencad2d.json`.
- Block references are persisted as normal entities.
- The canvas renders a block reference by transforming the entities from the referenced definition into world coordinates.
- A block reference can be transformed by existing transform commands because it implements `CadEntity.Transform(...)`.
- Hit testing uses the transformed definition bounding box.

### Deliberately deferred

- Create Block UI.
- Insert Block UI.
- Edit Block mode.
- Block Manager is now implemented as the v0.8.113 minimal manager.
- Attribute definitions.
- Nested block recursion policy.
- Edit Block mode.
- DXF/SVG/PDF export expansion of block references.

The next recommended milestone is `v0.8.111 — Create Block from selection`.

## Implementation checkpoint — v0.8.111 Create Block from selection

The second implementation checkpoint makes the block model usable from the main UI without introducing the full block editing workflow yet.

### Added workflow

```text
1. Select one or more editable entities.
2. Click Create Block.
3. Enter a block name.
4. Either type base point X/Y or click `Pick base point from drawing`.
5. If picking from drawing, click the canvas; active snaps can define the picked point.
6. OpenCad2D creates a BlockDefinition in local block coordinates.
7. The original selected entities are replaced by one BlockReferenceEntity.
8. The new block reference is selected.
```

### Geometry rule

The selected world-space geometry is translated by `-basePoint` before being stored in the block definition. The inserted block reference is then placed at `basePoint` with identity X/Y axes. This means the visible drawing does not move when the block is created.

### Undo rule

Create Block is executed as one undoable command. Undo removes the created block reference, restores the original selected entities, and removes the newly created block definition.

### Current limitations

- Base point can be entered numerically or picked from the canvas.
- Nested blocks are rejected for now.
- Create Block, Insert Block, the minimal Block Manager, internal block snapping and Explode Block are implemented. Edit Block remains a separate future milestone.

## Implementation checkpoint — v0.8.111.1 Create Block picked base point

Create Block now supports a hybrid base point workflow. The options dialog keeps numeric X/Y fields, but also provides `Pick base point from drawing`. When that button is used, the dialog closes, the main canvas enters a pending base-point-pick state, and the next click commits `CreateBlockFromSelection` with the picked point. Active snaps are honored. Escape cancels the pending create-block operation without modifying the document.

## Implementation checkpoint — v0.8.112 Insert Block

`Insert Block` is now available as the second user-facing block workflow. It inserts a new `BlockReferenceEntity` from an existing `BlockDefinition` without duplicating the definition geometry.

Implemented workflow:

1. User clicks `Insert Block`.
2. OpenCad2D shows an `Insert Block` options dialog.
3. User selects an existing block definition.
4. User enters uniform `Scale` and `Rotation °` values.
5. After OK, the canvas enters a pending insertion-point state.
6. The next canvas click creates the new block reference.
7. Active snap candidates are honored for the insertion point.
8. Escape cancels the pending insert without modifying the document.

The new reference stores the chosen insertion point, a scaled/rotated local X axis and a scaled/rotated local Y axis. The referenced definition remains shared. Undo removes only the newly inserted instance and keeps the original block definition and existing references.

Still future work:

- live preview while choosing insertion point;
- Edit Block definition.

## Implementation checkpoint — v0.8.114/v0.8.115 Internal snapping and Explode Block

Block references now participate in direct geometry workflows instead of only behaving like rectangular containers. Hit testing, selection-by-click and snap candidates can use transformed child geometry exposed by the block definition. Endpoint, midpoint, center and nearest snapping work on supported internal entities while the selected/snapped target remains the block reference at document level.

Explode now accepts selected `BlockReferenceEntity` instances in addition to polylines. Running `EXPLODE`/`X` on a block reference removes only the selected reference and adds fresh-ID world-space copies of the definition entities transformed by the reference insertion point, scale and rotation axes. The block definition itself remains in the document so other references continue to work and the operation is undoable as one modify command.

Current limitation: Edit Block is still pending. Explode is intentionally the first block-editing workflow because it is deterministic, easy to test and useful before a full isolated block editor exists.
