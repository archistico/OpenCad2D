# Specification — v0.8.200 HatchEntity and Hatch Patterns

## Purpose

Introduce a real hatch entity similar in purpose to AutoCAD HATCH while keeping the first implementation conservative and testable. Boundary Fill v2 already creates filled closed polylines from detected regions. `HatchEntity` is a separate model that can represent hatch-specific data such as holes, islands, patterns, pattern scale and pattern angle.

## Shared contracts

Hatch tools must follow:

- `shared-preview-and-commit-workflow.md` for preview, validation, commit and grouped undo;
- existing draw-order, layer, color and export rules;
- Boundary Fill v2 documentation for the distinction between region detection and hatch persistence.

## Design decisions

- Hatch is a persistent entity, not just generated linework.
- Boundary Fill v2 keeps its current filled-polyline output until an explicit option to create HatchEntity is added later.
- First hatch patterns are built-in and small. Full AutoCAD `.pat` compatibility is deferred.
- First implementation may store sampled loops if native loop segments are not ready, but the sampling tolerance must be centralized and documented.
- Associativity to boundary source entities is deferred.

## Entity model

Suggested persistent model:

```text
HatchEntity
- Id
- LayerId
- Color/appearance inheritance
- OuterLoops
- InnerLoops
- FillMode: Solid | Pattern
- PatternName
- PatternScale
- PatternAngle
- Origin optional/deferred
- BoundarySourceIds optional/deferred
```

Loop model options:

| Option | Pros | Cons |
|---|---|---|
| Sampled points | simpler, matches current curve sampling capabilities | less precise, larger files, harder DXF semantic export |
| Native segments | better precision and export potential | more implementation work |

Recommended first path: sampled loops if it allows a stable first milestone, with a clear migration path to native segments later.

## Loop requirements

At minimum:

- one outer loop is required;
- zero or more inner loops may create holes;
- loops must be closed;
- invalid/self-intersecting loops should be rejected unless there is robust handling;
- inner loops outside the outer loop should be rejected;
- overlapping inner loops should be rejected or documented as unsupported.

## Creation modes

Recommended order:

1. create hatch from one selected closed polyline;
2. create hatch from selected circle/ellipse/polyline loops;
3. select outer loop plus explicit inner loops;
4. assemble one loop from connected line/arc/polyline entities;
5. later: click-inside region detection that can output HatchEntity instead of filled polyline.

Do not attempt all modes in the first slice.

## Pattern scope

First built-in pattern set:

```text
SOLID
ANSI31
ANSI32
HORIZONTAL
VERTICAL
CROSS
GRID
DOTS
BRICK
CONCRETE_SIMPLE
EARTH_SIMPLE
```

The first code slice may implement fewer patterns if needed, but `SOLID`, `ANSI31`, `HORIZONTAL`, `VERTICAL` and `CROSS` should be the minimum useful set.

Pattern parameters:

| Parameter | Meaning |
|---|---|
| `PatternName` | built-in pattern key |
| `PatternScale` | model-space scale multiplier, > 0 |
| `PatternAngle` | rotation in degrees |

## Rendering strategy

Solid hatches render as filled clipped areas. Pattern hatches can render as generated linework clipped to the hatch loops. The pattern generation should be deterministic so save/reopen and export do not produce visually unstable results.

The clipping implementation is central. If clipping cannot support holes reliably, implement solid outer loop first and delay inner loops/patterns until clipping is safe.

## Property Panel

Expose:

- fill mode;
- pattern name;
- pattern scale;
- pattern angle;
- layer/color/appearance according to existing entity rules;
- optional source/loop diagnostics later.

Edits should update rendering immediately and be undoable.

## Relationship with Boundary Fill

`BFILL` remains completed with filled closed polyline output. Later, BFILL may gain an option:

```text
Output: Polyline | Hatch
```

That option must be explicit. It must not silently change existing user expectations or tests.

## Export behavior

| Export | First-version strategy |
|---|---|
| SVG | Export solid fills and generated pattern linework clipped to loops where possible. |
| PDF | Export solid fills and generated pattern linework. |
| PNG | Canvas rendering output. |
| DXF | Prefer DXF HATCH if reliable; otherwise export generated linework/solid fallback and document limitations. |
| Native JSON | Preserve HatchEntity loops and pattern properties. |

Visible output is more important than semantic DXF HATCH fidelity in the first pass.

## Implementation slices

| Slice | Goal |
|---|---|
| `v0.8.200A` | `HatchEntity` model, solid fill from one selected closed polyline, save/reopen, selection and draw order. |
| `v0.8.200B` | Inner loops/holes for explicitly selected closed loops. |
| `v0.8.200C` | Built-in line-based patterns with scale/angle and Property Panel editing. |
| `v0.8.200D` | Export behavior for SVG/PDF/PNG/DXF with documented fallbacks. |
| `v0.8.200E` | Optional BFILL output mode to create HatchEntity, only after HatchEntity is stable. |

## Test requirements

Automated tests should cover:

- closed polyline to solid hatch;
- invalid open loop rejection;
- inner loop hole rendering data;
- pattern scale/angle persistence;
- Property Panel edits;
- hit testing/selection;
- draw order interactions;
- save/reopen;
- export output contains visible hatch representation;
- undo/redo.

Manual tests should cover:

- hatch on common plan boundaries;
- hatch with one island/hole;
- pattern density at different scales;
- PDF/SVG visual checks;
- DXF open in LibreCAD/QCAD or another viewer and limitation recording.

## Exit criteria

The milestone is complete when users can create, edit, save/reopen and export real HatchEntity objects with solid and basic patterned fills, including at least one reliable inner-loop/hole workflow or a clearly deferred note if holes are split into the next slice.
