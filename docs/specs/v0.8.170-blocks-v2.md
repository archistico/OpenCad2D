# Specification — v0.8.170 Blocks v2

## Purpose

Improve block management so blocks become a reliable foundation for Library content, repeated symbols, future architectural objects and later UI workflows. Blocks v1 already supports block definitions, block references, Create Block, Insert Block, a minimal Block Manager, internal block snapping, Explode Block and a first Edit Block workflow. Blocks v2 should not rewrite that foundation; it should make management safer, more diagnosable and more predictable.

This milestone should be implemented before parametric doors/windows, Array tools and large Library expansion because those features depend on predictable block identity, conflict handling, preview and undo behavior.

## Shared contracts

Blocks v2 must follow:

- `shared-preview-and-commit-workflow.md` for preview/commit and grouped undo;
- `shared-anchor-system.md` if block insertion or Library insertion exposes 9-point anchors;
- existing `docs/specs/v0.8.110-blocks.md` for the v1 baseline.

## Goals

Blocks v2 should provide:

- a richer Block Manager with inventory, reference counts, preview and diagnostics;
- safe rename, duplicate and purge operations;
- clearer edit-session workflow and cancellation behavior;
- invalid/missing reference diagnostics;
- deterministic Library import conflict policy;
- grouped undo for multi-part block operations;
- manual and automated tests for block operations that can corrupt drawings if wrong.

## Non-goals

- Nested block editing beyond what can be made safe in small steps.
- Attribute blocks, dynamic block constraints or AutoCAD-compatible dynamic blocks.
- Full external references (`XREF`) behavior.
- Associative arrays of block references.
- Parametric doors/windows as block definitions. Those remain their own entities.

## Block Manager v2

### v0.8.170A implemented baseline

The first Blocks v2 slice improves the manager inventory without changing the block file model. The manager now shows direct drawing references, nested references from block definitions, total references, bounds, status and a selected-block details/diagnostics panel. Blocks used only inside another block are no longer treated as deletable. Empty definitions, missing nested references and recursive/self-referencing definitions are surfaced as diagnostics; recursive definitions are blocking and cannot be inserted or accepted from the manager.

This slice deliberately does not add duplicate, bulk purge, edit-session hardening, Library conflict handling or visual preview thumbnails yet. Those remain in later slices.

### v0.8.170B implemented baseline

The second Blocks v2 slice adds safe manager-side duplicate and purge operations while preserving the existing final commit model. The manager can duplicate the selected definition into a new definition with a new id, a unique `Copy` name and new internal entity ids; existing drawing references continue to point to the original definition.

`Delete Selected` remains intentionally conservative: it removes only a selected definition with no drawing references and no nested references. `Purge Unused` is broader and more useful: it computes the definitions reachable from model-space block references, follows nested block references, and removes every definition that is not reachable from the drawing as one manager-side update. This means an unused parent block and child block can be purged together, while a child block nested inside a drawing-used parent is preserved.

Blocking diagnostics are still rejected on OK/Insert when they affect retained definitions. Purge is allowed to remove unreachable invalid definitions as a recovery workflow, because removing a drawing-unreachable broken block definition cannot invalidate visible model-space references. The result still flows through `UpdateBlockDefinitionsCommand`, so accepting the manager after duplicate/purge is grouped into one undoable block-definition update.


### v0.8.170C implemented baseline

The third Blocks v2 slice hardens the in-place Edit Block session. The UI now exposes explicit enabled state for Edit, Save and Cancel so Save/Cancel are only available while a block edit session is active. The active session message states that Save commits session entities and Cancel discards them.

The save contract is intentionally safer than the original selection-driven behavior. At session start OpenCad2D records the model-space entity ids that already existed. During Save, the block definition is rebuilt only from entities that belong to the session: the original editable block contents plus entities created after the session started. Pre-existing external drawing entities are ignored even if they are selected. This prevents accidental absorption of unrelated model-space geometry into the block definition. During Cancel, session entities created while editing are discarded together with the temporary editable block contents, and the original block reference is restored.

The first hardened implementation still excludes nested `BlockReferenceEntity` instances from the rebuilt definition. Nested block editing/import policy remains a later Blocks v2 concern.

### v0.8.170D implemented baseline

The fourth Blocks v2 slice implements the first deterministic Library/block conflict policy. Library insertion no longer blindly reuses an existing `Library.<item id>` block definition when the source file has changed. The incoming Library item is first converted into the target document context, including the existing line format, text format, dimension style and layer merge/remap rules. OpenCad2D then compares the prepared block content with existing definitions while ignoring entity ids, which are intentionally regenerated during import.

The implemented policy is conservative and non-destructive:

| Case | Behavior |
|---|---|
| Same Library item id and equivalent definition | Reuse the existing definition and add only a new block reference. |
| Same Library item id but different definition | Create a new block definition with a unique id such as `Library.arredo.chair_2` and a unique name such as `Library/arredo/chair (2)`. |
| Same block name and equivalent definition, even with a different Library item id | Reuse the existing definition to avoid duplicate identical blocks. |
| Same block name but different definition | Create a unique name and preserve the existing definition unchanged. |
| Explicit replacement | Still deferred to a future Block Manager operation. Library insertion never overwrites silently. |

This keeps existing drawings stable when a Library file evolves after earlier insertions. Existing block references keep pointing to the definition that was present at the time of insertion. New insertions receive a safe renamed definition only when the incoming geometry/style content is actually different.

The Block Manager should show a useful inventory rather than only a minimal list. Recommended columns:

| Column | Meaning |
|---|---|
| Name | User-facing block name. |
| Drawing reference count | Number of model-space `BlockReference` entities using this definition. |
| Nested reference count | Number of references from inside block definitions using this definition. |
| Total reference count | Drawing reference count plus nested reference count. This governs safe delete/purge in the first implementation. |
| Status | Used, unused, invalid, missing referenced data, or reserved/internal if such state exists. |
| Entity count | Number of entities inside the definition. |
| Preview | Small generated preview thumbnail or preview area. |
| Source | Drawing, Library import, duplicated, or unknown if source tracking is not available. |

The first implementation can use a selected-block preview panel instead of a thumbnail in every row. The important point is that the user can inspect what a block contains before renaming, duplicating, purging or inserting it.

## Operations

### Rename

Rename changes the block definition name and updates all references coherently. It must reject:

- empty names;
- duplicate names unless an explicit overwrite/merge command exists;
- names with characters unsupported by save/export if such restrictions exist;
- renaming while an edit session is active if that would be ambiguous.

Undo must restore the old name and all references.

### Duplicate

Duplicate creates a new block definition with a new name and the same internal entities. Existing references remain attached to the original definition. The duplicate may optionally be inserted immediately, but that should be a separate explicit action unless the UI makes it clear.

### Purge

Purge deletes unused block definitions only. It must not delete definitions with active references. The UI should explain why a block cannot be purged when `Reference count > 0`.

Bulk purge is allowed if it previews the list of unused blocks and commits as one undoable operation.

### Delete definition

If a direct delete operation exists, it should behave like purge for unused definitions. Deleting a used definition should be blocked unless there is a future explicit operation that also deletes or explodes all references.

### Insert existing block

Insertion should use the same preview/commit workflow as Library insertion. If the shared anchor system is implemented before or during this milestone, insertion may expose the 9-point anchor selector. Otherwise it should preserve current insertion behavior and leave anchor integration for the next slice.

## Edit Block workflow

Edit Block should be made safer and more explicit.

Recommended states:

```text
Normal drawing
Entering block edit
Editing block definition
Previewing effect on references optional/deferred
Saving block edit
Cancelling block edit
Returning to normal drawing
```

Rules:

- the UI must clearly show that the user is editing a block definition, not ordinary model-space entities;
- save and cancel must be distinct;
- leaving the edit session with unsaved changes should ask or follow the existing save-changes convention;
- editing an empty block should either be prevented or clearly allowed with an explicit reason;
- unsupported entities inside blocks should be listed as diagnostics, not silently dropped;
- pre-existing external model-space entities must not be absorbed into the block definition by accidental selection;
- entities created during the edit session are session-scoped: Save may commit them to the definition, while Cancel discards them;
- undo after saving an edit should restore the previous definition and all references visually.

## Library import conflict policy

When inserting a Library item that creates or imports a block definition, use deterministic conflict handling:

| Case | Behavior |
|---|---|
| Same name and equivalent definition | Reuse existing definition. |
| Same name but different definition | Create a new unique name, for example `name_2`. |
| Missing or invalid name | Generate a safe name from file name and category. |
| User explicitly chooses replace | Defer until a later manager-only operation; never replace silently during insertion. |

Definition equivalence can start conservative. If exact structural comparison is too expensive or unavailable, compare a stable serialized signature or always treat same-name imports as potentially different and create a unique name. Do not silently overwrite.

## Invalid references and recovery

The Block Manager should detect and report:

- block references pointing to missing definitions;
- definitions with zero entities if considered invalid;
- unsupported nested or recursive definitions if possible;
- definitions containing entities that cannot currently be rendered/exported.

Recovery should favor preserving user data. Missing references can render as a diagnostic placeholder rather than crashing or disappearing silently.

## Persistence

Blocks v2 should not require a breaking file-format change unless absolutely necessary. New metadata such as source, preview cache or diagnostics should be optional and recoverable.

Do not persist preview bitmaps into `.opencad2d.json` in the first implementation. Generate previews from block geometry when needed.

## Export behavior

Export should continue to produce visible geometry correctly. DXF may export block definitions/references if the current exporter supports it; otherwise generated geometry fallback is acceptable if documented. SVG/PDF/PNG should reflect the canvas output.

## Test requirements

Automated tests should cover:

- drawing, nested and total reference count calculation;
- delete rejection for blocks referenced only inside other block definitions;
- empty block definition diagnostics;
- missing drawing and nested block-reference diagnostics;
- recursive block definition diagnostics and insertion/result rejection;
- rename preserves references because references are id-based and manager validation rejects duplicate/empty names;
- duplicate leaves old references unchanged and assigns new entity ids inside the copied definition;
- selected delete deletes only definitions with no drawing or nested references;
- purge deletes definitions not reachable from drawing block references, including unused nested block trees;
- purge preserves definitions reachable through drawing-used nested references;
- Library same item id with changed geometry creates a safe unique id and name;
- Library same name with equivalent geometry reuses the existing definition;
- Library same-name conflict with different geometry creates a safe unique name;
- missing definition diagnostic does not crash rendering/save;
- undo/redo for rename, duplicate and purge;
- Edit Block save ignores pre-existing external model-space selection;
- Edit Block save includes entities created during the active session;
- Edit Block cancel removes entities created during the active session;
- save/reopen after each operation.

Manual tests should cover:

- manager inventory on simple, nested, empty and recursive blocks;
- manager preview on simple and complex blocks once the preview panel is implemented;
- insert, explode and edit after rename;
- Library insertion conflict with an existing name;
- DXF/SVG/PDF export visibility;
- cancellation from edit mode;
- Save/Cancel buttons are disabled outside an active edit session and enabled inside one.

## Exit criteria

Blocks v2 is complete when a maintainer can inspect block inventory, safely rename/duplicate/purge definitions, diagnose invalid references, insert Library items without silent overwrites, and undo all block-management operations coherently.
