# Specification — v0.8.220 UI Customization

## Purpose

Make the OpenCad2D interface more customizable without breaking the stable command workflow. The inspiration is Blender-style customization: compact panels, icon-focused layouts, saved workspace preferences and user control over visible tool areas.

This milestone is UI-level only. It should not change drawing persistence or command semantics.

## Design decisions

- UI preferences are local application settings, not drawing-file data.
- Keyboard commands and aliases remain available even when panels are hidden.
- There must always be a reset command.
- First version should be controlled and robust; full arbitrary docking is deferred unless Avalonia layout support is made safe.

## Goals

Initial customization should support:

- toolbar mode: text + icons, icons only, optional compact mode;
- panel visibility preferences;
- remembered panel widths;
- remembered window bounds/state;
- reset UI layout command;
- workspace preset foundation, even if only one default workspace is shipped initially;
- persistent settings across restarts.

## Non-goals for first pass

- Full Blender-level arbitrary layout splitting.
- User scripting of UI panels.
- Runtime editing of every command group.
- Floating/docking panels if that destabilizes input focus.
- Replacing the Dynamic HUD interaction model.

## Settings model

Suggested local settings:

```text
ToolbarDisplayMode: TextAndIcons | IconsOnly | CompactIcons
LeftPanelVisible: bool
RightPanelVisible: bool
SnapBarVisible: bool
StatusBarVisible: bool optional/deferred
LeftPanelWidth: double
RightPanelWidth: double
LastWindowBounds
LastWindowState
WorkspaceName: string optional/deferred
```

Use the existing application settings infrastructure if possible. If the settings file becomes versioned, unknown values should fall back to defaults instead of preventing startup.

## UI behavior

### Text + icons

This remains the default safe mode. It is more discoverable and should be used after Reset UI.

### Icons only

Icons-only mode hides command text in toolbars/panels but keeps tooltips and command aliases. It should improve horizontal/vertical density without changing command grouping.

### Compact mode

Compact mode may reduce padding and button height/width. It must not make hit targets too small for practical use. If compact mode is risky, defer it after icons-only mode.

### Panel visibility

Users should be able to show/hide major panels:

- left tool panel;
- right Property Panel;
- snap bar if implemented as a separate area;
- Library panel/window if it becomes docked later.

Hidden panels should not disable the commands themselves. Commands remain available through keyboard aliases, menus or command palette/HUD.

### Reset UI

A visible `Reset UI layout` action must restore:

- default panel visibility;
- default toolbar text+icon mode;
- default panel widths;
- safe window layout.

If settings are corrupted, startup should fall back to the reset layout.

## Workspace presets

A lightweight workspace model can be introduced without full docking:

```text
Drafting
Annotation
Architecture
Minimal
```

First pass may only store the current/default workspace. Future passes can map each workspace to panel visibility and toolbar density.

## Interaction and focus rules

UI customization must not reintroduce HUD focus problems. Moving the mouse over panels or the HUD must not steal keyboard focus from active drawing commands unless the user explicitly enters a text field or control.

If panels become movable/dockable later, command capture and canvas focus must be regression-tested.

## Implementation slices

| Slice | Goal |
|---|---|
| `v0.8.220A` | Settings model for toolbar display mode, panel visibility and panel widths. |
| `v0.8.220B` | Icons-only mode with tooltips and safe fallback. |
| `v0.8.220C` | Panel visibility toggles and persistence across restarts. |
| `v0.8.220D` | Reset UI layout command and corrupted-setting recovery. |
| `v0.8.220E` | Optional workspace preset foundation and documentation. |

## Test requirements

Automated tests should cover settings serialization/deserialization and fallback from invalid values where practical.

Manual tests should cover:

- switching text+icon/icons-only;
- restarting application and preserving choice;
- hiding/showing panels;
- command aliases while panels are hidden;
- reset layout;
- active command behavior after UI mode changes;
- small and large window sizes.

## Exit criteria

The milestone is complete when users can switch to an icons-only interface, hide/show major panels, keep those preferences across restarts, and safely reset the UI if they dislike or break the layout.
