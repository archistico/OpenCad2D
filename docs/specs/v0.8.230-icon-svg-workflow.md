# Specification — v0.8.230 Icon SVG Workflow

## Purpose

Allow the current OpenCad2D icons to be exported as editable SVG files, modified externally by the maintainer/user, and reloaded into the application as a custom icon set. The goal is to make icon iteration easier without manually editing XAML path resources for every change.

This workflow belongs to UI customization. It must not affect drawing files.

## Design decisions

- Icon overrides are local application preferences, not `.opencad2d.json` data.
- Built-in icons are always available as fallback.
- Invalid SVG files must not crash startup or break the toolbar.
- Icon identity is based on stable command/tool keys, not display text.
- Imported SVG support should start with simple safe shapes/paths only.

## Folder and manifest model

Recommended export folder layout:

```text
icons-export/
  icons-manifest.json
  draw-line.svg
  draw-circle.svg
  draw-rectangle.svg
  modify-move.svg
  modify-copy.svg
  modify-trim.svg
  modify-extend.svg
```

Recommended custom folder layout:

```text
OpenCad2D-icons-custom/
  icons-manifest.json
  draw-line.svg
  modify-move.svg
  ...
```

The manifest should map stable icon keys to filenames and optional metadata:

```json
{
  "version": 1,
  "icons": {
    "draw.line": "draw-line.svg",
    "modify.move": "modify-move.svg"
  }
}
```

The exact key names should come from command identifiers, not translated labels.

## Export behavior

The export command should:

- write one SVG per built-in icon;
- write `icons-manifest.json`;
- use stable filenames;
- include a simple `viewBox`;
- avoid embedding fonts, scripts, rasters or external references;
- preserve monochrome/current-color behavior where possible;
- report how many icons were exported and where.

Export can be developer-facing first. It does not need to be perfect for all icons before the import fallback is safe.

## Import behavior

The import command should:

- accept a folder path;
- read `icons-manifest.json` if present;
- load icons by stable key;
- validate each SVG independently;
- reject invalid icons with diagnostics;
- use built-in icons for missing/invalid replacements;
- persist the chosen custom icon folder in local application settings;
- provide a reset-to-built-in option.

If there is no manifest, a fallback filename convention may be allowed, but the manifest should be the reliable workflow.

## SVG validation

First pass should support simple safe SVG constructs:

- `svg` root with `viewBox`;
- `path` with supported path data;
- simple `rect`, `circle`, `line`, `polyline`, `polygon` if the renderer supports them;
- inline fill/stroke attributes if safe.

Reject or ignore:

- scripts;
- external references;
- embedded raster images;
- remote URLs;
- CSS that cannot be interpreted safely;
- animations;
- extremely large files;
- malformed XML.

Validation must happen before the icon is used in the UI.

## Rendering strategy

If Avalonia can render SVG directly through an existing safe library, use it only after validation. If built-in icons are currently XAML path resources, export/import may need a conversion layer. The implementation should choose the smallest stable path:

1. export current path data to SVG;
2. import SVG path data back into the icon model;
3. fallback to built-in resource on error.

Do not add a heavy dependency only for icon import unless the tradeoff is documented.

## Settings

Suggested local settings:

```text
CustomIconFolder
UseCustomIcons: bool
LastIconImportDiagnostics optional/deferred
```

Corrupted settings or missing folders should fall back to built-in icons and show a non-blocking diagnostic.

## Implementation slices

| Slice | Goal |
|---|---|
| `v0.8.230A` | Stable icon key inventory and manifest schema. |
| `v0.8.230B` | Export built-in icons to SVG + manifest. |
| `v0.8.230C` | Import/validate custom SVG folder with built-in fallback. |
| `v0.8.230D` | Settings persistence, reset to built-in and diagnostics UI. |
| `v0.8.230E` | Documentation and manual checklist. |

## Test requirements

Automated tests should cover:

- manifest generation;
- known icon key mapping;
- valid SVG accepted;
- invalid SVG rejected;
- missing icon falls back to built-in;
- malformed manifest fallback;
- settings load with missing custom folder;
- reset-to-built-in behavior.

Manual tests should cover:

- export all current icons;
- edit one icon externally and reload;
- import folder with one invalid SVG;
- restart application with custom icons active;
- reset to built-in icons;
- icons-only UI mode interaction if v0.8.220 is already implemented.

## Exit criteria

The milestone is complete when the current icon set can be exported to SVG, at least one modified SVG can be imported and displayed, invalid icons cannot break the UI, and users can reset safely to the built-in icon set.
