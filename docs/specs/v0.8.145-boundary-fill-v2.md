# v0.8.145 — Boundary Fill v2

Boundary Fill v2 improves the existing click-inside fill workflow without introducing a real `HatchEntity` yet. The output remains a filled closed `PolylineEntity`; `HatchEntity`, holes/islands and associative hatches remain the next milestone.

## Current implementation status

Boundary Fill v1 is implemented and creates a filled closed polyline from visible linear boundaries around a seed point. The v2 work is being added in small, testable steps.

Completed so far:

- `BoundaryFillOptions` separates geometry tolerance, future gap tolerance, curve-boundary enablement and curve sample count.
- `BoundaryFillResult` now exposes a machine-readable status, seed point, boundary vertices and diagnostics while preserving the previous `Succeeded`, `Polyline` and `Message` API.
- `BoundarySegmentCollector` centralizes boundary segment extraction and keeps metadata for each segment.
- `CircleEntity`, `ArcEntity` and bulged `PolylineEntity` can be sampled into boundary segments when `IncludeCurveBoundaries` is enabled.

The interactive `BoundaryFillTool` still uses the conservative v1 workflow until preview and diagnostic states are added. Curve boundary support is currently available at service/options level and is covered by core tests.

## Supported boundary sources

Boundary Fill v2 should treat the following entities as candidate boundaries:

- `LineEntity` as one straight segment.
- Straight `PolylineEntity` as one segment per edge, including the closing edge when closed.
- Bulged `PolylineEntity` as sampled line segments when curve boundaries are enabled.
- `CircleEntity` as sampled line segments when curve boundaries are enabled.
- `ArcEntity` as sampled line segments when curve boundaries are enabled.

The following are intentionally not boundary sources in this milestone:

- text and MTEXT;
- dimensions;
- images;
- block references, unless a later explicit virtual expansion step is designed;
- stair annotation segments such as arrows and section markers;
- future hatch entities.

## Result and diagnostics contract

`BoundaryFillResult` is the contract used by the future preview workflow. A successful result contains the created filled polyline, the seed point, the detected boundary vertices and diagnostic counters. Failures are classified with `BoundaryFillStatus` so the tool can eventually show precise HUD/status messages.

Diagnostics currently include source segment count, graph edge count, candidate face count, ignored entity count, bridged gap count, sampled curve segment count and gap tolerance. `BridgedGapCount` is reserved for the gap-tolerance step and remains zero until endpoint clustering is implemented.

## Curve sampling policy

Curve boundaries are sampled only when `BoundaryFillOptions.IncludeCurveBoundaries` is true. This keeps the current tool conservative while allowing the core algorithm to be tested on curves.

Sampling uses `BoundaryFillOptions.CurveSampleCount` as the full-circle budget. Circles receive that number of segments. Arcs receive a proportional number of segments based on their sweep, with a minimum of two segments. Sampled segments are marked with `IsSampledCurve = true` and keep the source entity id/kind.

## Remaining v2 work

The remaining steps are:

1. endpoint clustering and small-gap tolerance;
2. preview result state in the tool;
3. HUD/status diagnostics;
4. confirmation workflow before creating the filled polyline;
5. final user guide and manual checklist.
