# Specification — v0.8.145 Boundary Fill v2

## Purpose

Boundary Fill v2 improves the existing click-inside `BFILL` workflow without introducing the future `HatchEntity` yet. The feature remains a bridge between the current solid-fill closed-polyline model and the later hatch system.

The v2 goal is practical CAD reliability: the user should be able to click inside a supported closed region, see the detected boundary before committing, receive clear diagnostics when detection fails, and use common curved boundaries such as arcs and circles through a controlled sampled approximation.

## Current v1 audit

The current implementation is centered on `BoundaryFillService.CreateFilledPolyline(...)` and `BoundaryFillTool`.

Implemented behavior:

- the command aliases `BFILL`, `BF`, `BOUNDARYFILL`, `FILL` and `RIEMPIMENTO` activate Boundary Fill;
- the tool asks for one seed point through click or command/HUD coordinate input;
- visible document entities are passed to `BoundaryFillService`;
- the service collects usable boundary segments from standalone `LineEntity` objects and straight `PolylineEntity` objects;
- straight rectangles and polygons work because they are closed polylines;
- linear segments are split at segment intersections;
- a planar graph is built from the split segments;
- interior faces are traced;
- the smallest face containing the seed point is selected;
- the result is emitted as a closed `PolylineEntity` with `IsFilled = true` on the current layer;
- creation is undoable through `AddEntityCommand`.

Important current limits:

- arcs, circles, ellipses, elliptical arcs, Bezier splines, block references, dimensions, text, images and stair annotations are not boundary input;
- closed circular or arc-composed regions cannot be filled unless they have already been converted to straight polylines;
- there is no preview state: picking the point immediately creates the fill if detection succeeds;
- endpoint tolerance is the general `GeometryTolerance`, not a user-facing small-gap tolerance;
- gaps are not intentionally bridged as a first-class behavior;
- there is no classification of ignored entity kinds in the result message;
- holes/islands cannot be represented by the current single filled `PolylineEntity` output;
- the generated fill is not associative with its source boundaries.

These limits are acceptable for v1, but v2 should make them explicit and improve the ones that fit the current output model.

## Scope

Boundary Fill v2 should deliver:

- preview of the detected boundary before creation;
- sampled arc and circle boundaries;
- conservative small-gap tolerance for endpoint clustering;
- clear diagnostics for open, ambiguous, unsupported or too-large-gap boundaries;
- tests for the core algorithm and tool workflow;
- documentation of supported and ignored boundary entities.

Boundary Fill v2 should still emit a filled closed `PolylineEntity`. It must not introduce `HatchEntity`, hatch patterns, subtractive holes, or associative boundary updates.

## Non-goals

The following are explicitly out of scope for v2:

- real `HatchEntity`;
- hatch pattern libraries;
- holes and islands;
- associative fill that updates when source boundaries change;
- boundary extraction from block references;
- boundary extraction from dimensions, text, MTEXT, raster images or symbol annotation linework;
- full AutoCAD-style boundary detection across arbitrary nested/overlapping objects;
- DXF `HATCH` export beyond the current closed-polyline solid-fill export path.

These belong to `v0.8.150 HatchEntity` or later.

## Supported boundary entities

The v2 boundary collector should support:

| Entity | v2 behavior |
|---|---|
| `LineEntity` | one analytic segment |
| straight `PolylineEntity` | one segment per edge, including closing edge when closed |
| mixed/bulged `PolylineEntity` | use straight edges natively and sampled arc edges where available through existing polyline geometry helpers, or defer mixed support if the extraction is not already stable |
| `CircleEntity` | sampled closed loop |
| `ArcEntity` | sampled open curve segment |
| rectangles/polygons | already represented as closed polylines |

Initially excluded:

| Entity | Reason |
|---|---|
| `EllipseEntity` / `EllipticalArcEntity` | can be sampled later, but should not be mixed into the first v2 algorithm until arcs/circles are stable |
| `BezierSplineEntity` | sampling and self-intersection behavior need separate tolerance policy |
| `BlockReferenceEntity` | virtual expansion may be useful later, but must respect layer visibility/locking and nested transforms |
| `DimensionEntity` and annotation entities | should not become room/fill boundaries by accident |
| `TextEntity` / `MTextEntity` | text is annotation, not boundary geometry |
| `ImageReferenceEntity` | raster references are not vector boundaries |
| `StairEntity` annotation segments | direction arrows and section markers must not affect fill detection; primary stair linework can be considered only in a future explicit architectural-boundary policy |

## Boundary segment model

Introduce an explicit internal segment representation instead of reusing the current private two-point record directly everywhere:

```text
BoundarySegment
- Start
- End
- SourceEntityId
- SourceKind
- IsSampledCurve
- SourceParameterStart optional/deferred
- SourceParameterEnd optional/deferred
```

The first version only needs start/end plus enough metadata to report diagnostics. Source metadata helps explain messages such as "unsupported entities ignored" or "sampled curve boundary used" and will later help bridge toward `HatchEntity`.

## Curve sampling policy

Curves are sampled into line segments for v2. The result is still an approximation because the output entity is a filled polyline.

Recommended policy:

- use a central sampling helper for Boundary Fill instead of ad-hoc loops in the tool;
- use a bounded maximum segment count to protect performance;
- choose segment count from radius and sweep angle when possible;
- preserve endpoints exactly for arcs;
- generate circles as closed sampled loops without duplicating the final point if the downstream loop code already closes them;
- record whether a segment came from sampled curve geometry.

The sampling tolerance should be documented and should not silently depend on current zoom. Boundary detection must be model-space deterministic.

## Gap tolerance

Boundary Fill v2 should distinguish two tolerances:

```text
GeometryTolerance
- low-level numeric tolerance for equality, collinearity and intersection calculations.

BoundaryFillGapTolerance
- user/tool-level tolerance for intentionally bridging small endpoint gaps.
```

Recommended first implementation:

- introduce a `BoundaryFillOptions` value object with `GapTolerance` and curve sampling settings;
- use a conservative default gap tolerance;
- do not persist it globally in v2 unless the settings system already has an obvious place;
- allow a later HUD option `Gap`/`Tolerance` to edit it during the command.

Endpoint clustering rules:

- endpoints within `GapTolerance` may be treated as the same graph node;
- the normalized node can be the first point or a weighted/average point, but the choice must be deterministic;
- if one endpoint is within tolerance of multiple candidate endpoints and the closest candidate is not clearly unique, the boundary should fail as ambiguous rather than guessing;
- gaps larger than `GapTolerance` should fail with a clear message.

Diagnostics should record whether any gaps were bridged. The preview can later expose this visually, but the first v2 implementation may only report it in the result metadata/message.

## Loop detection

The current planar-face approach is a good base and should not be replaced without need. v2 should evolve it rather than implementing an unrelated second algorithm.

Recommended algorithm:

1. collect boundary segments;
2. sample supported curves into boundary segments;
3. split segments at intersections;
4. cluster endpoints using numeric tolerance and optional gap tolerance;
5. build a planar graph;
6. trace interior faces;
7. discard degenerate/self-intersecting faces where detected;
8. choose the smallest valid face containing the seed point.

The "smallest containing face" rule should remain because it handles subdivided rooms and nested simple loops better than choosing the first hit.

## Preview workflow

Current v1 creates the fill immediately after the seed point. v2 should add a preview phase.

Target interaction:

```text
BFILL
move mouse or enter seed X/Y
preview boundary if one is found
Enter or right click confirms
Esc cancels
```

Tool states:

```text
WaitingForSeedPoint
PreviewReady
NoBoundaryFound
Confirmed
Cancelled
```

Rules:

- preview must be transient and must not add an entity to the document;
- preview should use the same service result that creation will use;
- moving the pointer should update preview cheaply enough for typical drawings;
- confirmation should create exactly the previewed filled polyline;
- if the preview is invalid, Enter/right click should not create anything.

If real-time hover preview is too expensive in the first implementation, a click-to-preview then Enter/right-click-to-confirm workflow is acceptable as the first v2 vertical slice. The important improvement is that detection and creation become separate phases.

## Result model

The existing `BoundaryFillResult` should probably be expanded or replaced by a richer result type:

```text
BoundaryFillDetectionResult
- Status: Success / NoBoundary / UnsupportedOnly / OpenBoundary / Ambiguous / Degenerate
- PreviewPolyline optional
- Message
- Diagnostics
- BridgedGapCount
- IgnoredEntityCount
- UsedSampledCurveCount
```

Creation can then reuse the detected `PreviewPolyline` instead of recomputing on confirmation.

The final committed entity remains:

```text
PolylineEntity
- IsClosed = true
- IsFilled = true
- LayerId = current layer
```

## Diagnostics

Minimum diagnostic messages:

```text
Boundary fill needs visible supported boundary entities.
No closed boundary was found around the picked point.
The selected point is outside all closed boundaries.
The detected boundary is degenerate.
The boundary has endpoint gaps larger than the current tolerance.
The boundary is ambiguous near the picked point.
Unsupported entities were ignored.
Curved boundaries were approximated for Boundary Fill.
```

Messages should be concise in the status/HUD, with tests checking exact strings only where the project already treats those strings as stable.

## HUD and command input

The command remains command-driven and HUD compatible.

Required behavior:

- X/Y coordinate entry for seed point remains supported;
- the HUD remains mouse-transparent until TAB enters editable fields;
- Enter/right-click confirms only when a valid preview exists;
- Esc cancels preview or the tool;
- future option `Gap` can expose the gap tolerance, but this may be implemented after preview/curve support if needed.

## Testing plan

Core tests:

- four independent lines forming a rectangle still work;
- straight closed polyline works;
- non-ordered line loop works;
- interior divider chooses the containing face;
- seed outside all boundaries fails;
- open boundary fails;
- line rectangle with a small endpoint gap succeeds when within `GapTolerance`;
- the same gap fails when above `GapTolerance`;
- ambiguous endpoint clustering fails instead of guessing;
- circle boundary creates a filled closed polyline approximation;
- arc plus line segments can form a filled region;
- unsupported entities are ignored but reported;
- unsupported-only input fails clearly;
- stair annotation segments do not participate in boundary detection.

Tool/ViewModel tests:

- seed coordinate input creates a preview rather than immediate creation once preview mode is introduced;
- valid preview confirmed with Enter creates one filled polyline;
- valid preview confirmed with right click creates one filled polyline;
- Esc cancels preview without modifying the document;
- invalid preview reports a message and confirmation does nothing;
- undo removes the committed filled polyline;
- aliases remain registered.

Manual smoke tests:

- rectangle from four lines;
- two rooms sharing a wall;
- rectangle with a small gap;
- rectangle with a gap above tolerance;
- circle boundary;
- arc plus lines;
- nested rectangles;
- click outside every boundary;
- save/reopen generated fills;
- SVG/PDF/DXF export of generated filled polylines.


## Implementation checkpoint — v0.8.145-B

The first implementation step after the audit introduces the result/options foundation without changing the visible v1 workflow.

Implemented in this checkpoint:

- `BoundaryFillOptions` carries the low-level `GeometryTolerance`, the future explicit `GapTolerance`, and reserved curve-sampling settings;
- `BoundaryFillStatus` classifies the detection outcome independently from the final message string;
- `BoundaryFillDiagnostics` records source segment count, graph edge count, candidate face count, ignored entity count, bridged gap count, sampled curve segment count and the active gap tolerance;
- `BoundaryFillResult` now exposes status, seed point, detected boundary vertices and diagnostics while keeping the existing `Polyline`/`Message`/`Succeeded` contract;
- existing callers can still use the old `GeometryTolerance?` overload;
- Boundary Fill still creates the same filled closed `PolylineEntity` immediately after a valid seed point.

This checkpoint is deliberately preparatory. It does not yet add curve boundaries, intentional gap bridging or preview confirmation.

## Implementation sequence

Use small steps:

1. **Audit/spec** — this document plus roadmap/handoff reconciliation.
2. **Boundary options/result model** — implemented: options, status and diagnostics exist without changing visible behavior.
3. **Boundary segment collector** — centralize supported/ignored entity extraction and prepare metadata.
4. **Curve sampling** — add circle and arc support behind core tests.
5. **Gap tolerance** — endpoint clustering and ambiguity detection.
6. **Preview phase** — separate detection from creation in the tool.
7. **HUD gap option** — optional if the core is stable enough.
8. **Documentation/manual checklist** — update user guide and known limitations.

## Exit criteria

Boundary Fill v2 can be marked complete when:

- the user can preview a detected boundary before committing;
- line, straight-polyline, arc and circle boundaries are supported in documented cases;
- small endpoint gaps can be bridged within a controlled tolerance;
- unsupported and ambiguous cases fail predictably;
- the committed output remains a normal filled closed polyline;
- automated tests cover the core cases and the tool confirmation/cancel flow;
- known limitations clearly say that holes/islands and real hatch entities remain deferred.
