# Specification — v0.8.140 Hatch and Boundary Fill

## Purpose

Introduce a real hatch/fill system that can represent filled regions, holes and composite boundaries made from multiple entities.

This milestone should be approached conservatively. A robust explicit-boundary hatch is preferable to an unreliable AutoCAD-style click-inside workflow.

## Long-term goal

Eventually, OpenCad2D should support:

- boundaries made from different entities;
- holes/islands;
- boundaries composed of lines, arcs, circles, ellipses, elliptical arcs and polylines;
- solid fills;
- hatch patterns;
- click-inside boundary detection.

## Initial scope: Hatch v1

Hatch v1 should support:

- explicit selected boundary;
- solid fill;
- one outer loop;
- optional explicitly selected inner loops if loop assembly is stable;
- rendering on canvas;
- persistence;
- selection/hit testing;
- SVG/PDF export;
- clear unsupported-boundary messages.

## Entity model

Suggested entity:

```text
HatchEntity
- Id
- LayerId
- FillMode: Solid initially
- OuterLoop
- InnerLoops
- BoundarySourceIds optional/deferred
```

Loop representation should be independent from the original entities so that the hatch remains stable even if the original boundary is later modified.

Suggested loop primitives:

```text
HatchLineSegment
HatchArcSegment
HatchEllipseSegment optional/deferred
HatchSampledCurveSegment optional
```

Alternative simpler v1 representation:

```text
Loop as sampled polygon points
```

Opinion:

A sampled polygon loop is easier for rendering, containment and holes. Native curve loop segments preserve precision better. The first version can use sampled loops internally if the sampling tolerance is documented and stable.

## Boundary creation modes

### Mode A — Closed polyline

The simplest path:

1. User selects one closed polyline.
2. User runs Hatch.
3. Application creates a hatch from the polyline vertices.

This should be the first testable vertical slice.

### Mode B — Selected connected entities

Next:

1. User selects lines/arcs/polylines/circles/ellipses.
2. Application tries to assemble one or more closed loops.
3. If exactly one valid outer loop is found, create hatch.
4. If multiple loops are found, classify outer/inner loops if possible or ask user to confirm later.

### Mode C — Click inside boundary

Deferred.

This requires:

- planar graph construction;
- intersection detection;
- virtual splitting of curves at intersections;
- face extraction;
- tolerance-safe loop selection;
- island detection.

Do not implement this first.

## Holes and islands

Hatch v2 should support inner loops.

Rules:

- Outer loop defines filled region.
- Inner loops subtract holes.
- Loop orientation should be normalized internally.
- Containment checks classify inner loops.
- Ambiguous overlapping loops should fail with a clear message.

Examples:

- rectangle outer + circle inner = rectangular fill with circular hole;
- polyline outer + ellipse inner = fill with elliptical hole;
- composed line/arc loop outer + closed polyline inner = valid hatch if loops are closed.

## Curve support

Recommended progression:

1. Closed polylines.
2. Lines assembled into polygon loops.
3. Arcs sampled into polyline segments.
4. Circles sampled as closed loops.
5. Ellipses sampled as closed loops.
6. Elliptical arcs sampled as partial loop segments.
7. Bezier splines deferred or sampled only with strict tolerance.

Sampling tolerance should be centralized and documented.

## Rendering

Canvas rendering must support:

- solid fill color from layer or hatch property;
- holes;
- selection outline/highlight;
- draw order/Z-order like other entities.

If a hatch has holes, rendering should use an even-odd fill rule or equivalent geometry composition.

## Persistence

Native JSON should persist:

- hatch loops;
- fill mode;
- layer;
- optional boundary source IDs if implemented;
- sampling tolerance/version if useful.

A saved hatch should reload without requiring the original boundary entities.

## Export

SVG:

- export as `<path>` with outer and inner loops;
- use even-odd fill rule where necessary.

PDF:

- export solid filled paths with holes if the PDF backend supports it.

DXF:

- export as HATCH where possible;
- if complex curves are sampled, export polyline boundary paths.

## Editing

Initial editing:

- Move/copy/rotate/scale/mirror hatch as a standalone entity.
- No associative boundary update.

Deferred:

- edit hatch boundary vertices;
- edit hatch pattern;
- associative rebuild from boundary source entities.

## Testing checklist

Core tests:

- hatch from closed polyline;
- hatch rejects open polyline;
- hatch from connected line loop;
- hatch rejects non-closed selected line set;
- hatch with inner loop classifies hole;
- point-in-region respects holes;
- transform hatch loops;
- persistence round-trip.

Export tests:

- SVG path contains fill and hole rule;
- PDF export includes solid fill;
- DXF export writes HATCH for simple loops.

Interaction tests:

- selected closed polyline -> hatch;
- selected boundary set -> hatch;
- undo removes hatch;
- hatch is selectable and transformable.

Manual tests:

- rectangle fill;
- rectangle with circular hole;
- line/arc composed boundary;
- ellipse hole;
- save/reopen;
- export SVG/PDF/DXF and inspect in viewers.

## Accepted first-version limitations

- No pattern hatches in v1.
- No full AutoCAD-style click-inside boundary detection in v1.
- No associativity in v1.
- Bezier boundaries may be deferred.
- Complex self-intersecting boundaries should be rejected.
