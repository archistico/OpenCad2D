# v0.8.121 Dynamic Command HUD and Command UX unification

Status: planned.

This milestone replaces the fixed bottom command row with a dynamic cursor-adjacent command HUD, but only after the command-state contract has been made coherent across all interactive tools.

The goal is not to build a special HUD for only Line, Polyline, Rectangle and Circle. The goal is to make every command-driven tool expose a consistent prompt, expected input, options, confirmation policy and live measurement state, then render that state through one HUD UI.

---

## Design principles

1. **One command state source**
   - Tool phases must be described by `CommandPromptState`.
   - The old `MainWindowViewModel.CommandPromptText` must stop owning tool-specific fallback behavior over time.
   - The UI must render the current command state; it must not infer command phases independently.

2. **No behavioral regression**
   - Existing command aliases, typed coordinates, relative input, polar input, direct distances, command history, autocomplete, right click, Enter and Escape behavior must keep working.
   - Mouse input and typed input must continue feeding the same tool state machines.
   - The old command row must remain available until the HUD has passed manual regression.

3. **Small reversible steps**
   - First add data propagation and read-only HUD state.
   - Then add a read-only visual HUD.
   - Only then move the real command input into the HUD.
   - Editable HUD numeric fields are a later milestone because they introduce new override semantics.

4. **All tools, not only draw tools**
   - Draw, dimension, transform, modify, measure, navigation and selection/order tools must be reviewed.
   - The HUD can be hidden for idle and normal selection, but command-driven tools should expose coherent prompt state even when no live measurement fields are shown.

---

## Milestone sequence

### HUD-0 — Tool prompt inventory

Status: planned.

Create or update a command UX inventory that lists every registered command-driven tool with:

- command name and aliases;
- internal phases;
- prompt text for each phase;
- expected input kind;
- options and shortcuts;
- whether empty Enter/right click is accepted;
- Escape behavior;
- snap mode expectations;
- live HUD fields, if any.

Exit criteria:

- The inventory covers draw, dimension, transform, modify, measure, navigation and selection/order tools.
- Any tool still relying on ViewModel-specific prompt fallback is explicitly identified.
- The next implementation step can be done without guessing command behavior.

---

### HUD-1 — Shared prompt contract cleanup

Status: planned.

Make `CommandPromptState` the common source for the current prompt.

Scope:

- Add or correct `GetPromptState()` implementations for all primary interactive tools.
- Normalize option names and shortcuts across tools.
- Keep existing localized aliases and command aliases unchanged.
- Add tests where practical for tool prompt phases that previously had implicit behavior.

Exit criteria:

- `MainWindowViewModel.GetCurrentPromptState()` can return a meaningful state for the active tool.
- `CommandPromptText` is mostly a formatted view of `CommandPromptState`, not a second source of truth.
- Existing command-input tests still pass.

---

### HUD-2 — Pointer screen position and live measurement data

Status: planned.

Prepare the data required by a cursor-adjacent HUD without changing the visible UI.

Scope:

- Add `PointerScreenPosition` to `CadCanvasWorkspaceChangedEventArgs`.
- Propagate the canvas pointer screen position from `CadCanvas` to `MainWindowViewModel`.
- Add `HudScreenPosition` to `MainWindowViewModel`.
- Extract live measurement calculation currently used by the status/measurement text into a reusable path.
- Compute live distance, angle, delta X and delta Y from the current base point to the snap-resolved/current mouse point, respecting the active tool input constraints.

Exit criteria:

- Build and tests pass.
- No visible UI behavior changes.
- Moving the mouse updates the HUD screen position in the ViewModel.
- Existing measurement/status text remains correct.

---

### HUD-3 — Read-only `CommandHudState`

Status: planned.

Introduce a ViewModel-level HUD model that is independent from Avalonia controls.

Recommended model:

```csharp
public sealed class CommandHudState
{
    public bool IsVisible { get; }
    public ToolId? ToolId { get; }
    public string? ToolName { get; }
    public string Prompt { get; }
    public IReadOnlyList<CommandOption> Options { get; }
    public IReadOnlyList<CommandHudField> Fields { get; }
    public string? Placeholder { get; }
}

public sealed class CommandHudField
{
    public string Key { get; }
    public string Label { get; }
    public double? LiveValue { get; }
    public string? Unit { get; }
    public bool IsEditable { get; }
}
```

Initial fields should be read-only. Direct editing belongs to HUD-7.

Exit criteria:

- The ViewModel can build a complete HUD state for the active command.
- Idle and selection visibility rules are explicit.
- Tool-specific field choices are centralized and testable.

---

### HUD-4 — Read-only visual HUD overlay

Status: planned.

Add the Avalonia overlay without moving the real command input yet.

Scope:

- Add a transparent overlay canvas above the CAD canvas.
- Render a compact HUD panel near the pointer with fixed offset.
- Clamp the panel inside the canvas/window bounds.
- Display icon, tool name, prompt, options and read-only live fields.
- Keep the old bottom command row fully functional.

Exit criteria:

- HUD follows the cursor.
- HUD does not block canvas input.
- Old command input behavior is unchanged.
- HUD is hidden for idle/normal selection according to the documented visibility rule.

---

### HUD-5 — Move the real command input into the HUD

Status: planned.

Move the existing `CommandInputTextBox` workflow into the HUD without creating a second command input.

Scope:

- Keep a single operational command input TextBox.
- Reuse existing key handling, focus management, history and autocomplete logic.
- Keep the old command row hidden or available only as a temporary fallback during the implementation branch.

Exit criteria:

- Typing command names and aliases works.
- Absolute, relative and polar coordinate input works.
- Direct distance input works.
- Command history with up/down works.
- Autocomplete with Tab works while idle.
- Enter, right click and Escape behavior remains unchanged.
- Manual regression passes for representative draw, modify, transform and measure tools.

---

### HUD-6 — Remove the old bottom command row

Status: planned.

Remove the old fixed bottom command row only after HUD-5 has passed regression.

Scope:

- Remove or permanently disable the old `Grid.Row` command row.
- Rebalance the main window layout if needed.
- Update README and UI documentation so they describe the dynamic HUD instead of the fixed command row.

Exit criteria:

- No duplicate command input remains.
- Main window layout has no empty command-row area.
- Documentation no longer describes the bottom row as the active command UI.

---

### HUD-7 — Editable numeric HUD fields

Status: deferred until the read-only HUD and moved command input are stable.

This is intentionally separated because editing HUD fields creates new semantics that are not equivalent to submitting a single command-input string.

Scope:

- Add field focus/Tab traversal for distance, angle, width, height, radius or other numeric fields.
- Add a `CommandHudInputOverride` model for temporary typed values.
- Freeze live field values while the user is editing them.
- Convert field overrides into target points or scalar command inputs only when the current tool supports that behavior.
- Implement tool by tool, starting with Line.

Recommended order:

1. Line: Distance + Angle.
2. Rectangle: Width + Height.
3. Circle: Radius.
4. Polyline line mode: Distance + Angle.
5. Rect Sides.
6. Arc / Arc 3P.
7. Move / Copy / Mirror target phases.
8. Rotate / Scale / Offset / Fillet / Chamfer scalar phases.

Exit criteria:

- Editing numeric fields does not break the normal command input.
- `1000 Tab 45 Enter` style workflows work only where explicitly supported.
- Tools without supported field overrides keep read-only fields.

## Initial live field policy

| Tool / phase family | Initial HUD fields |
|---|---|
| Line after first point | Distance, Angle |
| Polyline line segment | Distance, Angle |
| Polyline arc segment | Distance, Angle initially; richer arc fields later |
| Rectangle by opposite corners | Width, Height |
| Rectangle by sides, first side | Width, Angle |
| Rectangle by sides, second side | Height |
| Circle radius phase | Radius |
| Arc center/radius/angle phases | Radius, Angle where meaningful |
| Move / Copy target phase | Distance, Angle |
| Mirror second point | Distance, Angle |
| Rotate angle phase | Angle |
| Scale factor phase | Factor |
| Offset distance phase | Distance |
| Fillet radius phase | Radius |
| Chamfer distance phase | Distance or Distance 1 / Distance 2 depending on current mode |
| Measure distance | Distance, Angle |
| Selection / idle | Hidden or compact prompt only, according to final UX decision |

## Manual regression checklist

Before removing the old command row, validate at least:

- `LINE`: click-click, typed points, direct distance, polar input, Escape.
- `POLYLINE`: line mode, arc mode, Close, Undo, Enter/right-click finish.
- `RECTANGLE` and `RECT SIDES`: clicked points and typed numeric dimensions.
- `CIRCLE`, `ARC`, `ARC3P`: point input and typed scalar input where supported.
- `MOVE`, `COPY`, `ROTATE`, `SCALE`, `MIRROR`: selection-first and command-first flows.
- `TRIM`, `EXTEND`, `BREAK`, `OFFSET`, `FILLET`, `CHAMFER`: option phases, EntityOnly phases, previews and confirmation.
- `MEASUREDISTANCE`, `MEASUREENTITY`, `MEASUREAREA`, `MEASUREANGLE`.
- `ZOOMWINDOW` and `ZOOMEXTENTS`.
- Command history, autocomplete, empty Enter repeat, Esc cancellation and second-Esc selection clearing.

---

## Non-goals

- Do not rewrite the tool state machines only to support the HUD.
- Do not create duplicate command input boxes.
- Do not implement editable numeric HUD fields before the read-only HUD and moved command input are stable.
- Do not remove existing command-input tests; extend them.
- Do not make the HUD responsible for geometric decisions that belong in tools or input services.
