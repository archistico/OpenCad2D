# v0.8.121 Dynamic Command HUD and Command UX unification

Status: in progress — non-visual HUD data foundation started; shared prompt contract cleanup started.

This milestone replaces the fixed bottom command row with a dynamic cursor-adjacent command HUD, but only after the command-state contract has been made coherent across all interactive tools.

The goal is not to build a special HUD for only Line, Polyline, Rectangle and Circle. The goal is to make every command-driven tool expose a consistent prompt, expected input, options, confirmation policy and live measurement state, then render that state through one HUD UI.

---

## Design principles

1. **One command state source**
   - Tool phases must be described by `CommandPromptState`.
   - The old `MainWindowViewModel.CommandPromptText` must stop owning tool-specific fallback behavior over time.
   - The UI must render the current command state; it must not infer command phases independently.

2. **No behavioral regression**
   - Existing command aliases, typed coordinates, relative input, polar input, direct distances, command history, autocomplete, right click, Enter and Escape behavior must keep working.
   - Mouse input and typed input must continue feeding the same tool state machines.
   - The old command row must remain available until the HUD has passed manual regression.

3. **Small reversible steps**
   - First add data propagation and read-only HUD state.
   - Then add a read-only visual HUD.
   - Only then move the real command input into the HUD.
   - Editable HUD numeric fields are a later milestone because they introduce new override semantics.

4. **All tools, not only draw tools**
   - Draw, dimension, transform, modify, measure, navigation and selection/order tools must be reviewed.
   - The HUD can be hidden for idle and normal selection, but command-driven tools should expose coherent prompt state even when no live measurement fields are shown.

### HUD-3 — Read-only `CommandHudState`

Status: in progress.

Introduce a ViewModel-level HUD model that is independent from Avalonia controls.

Recommended model:

```csharp
public sealed class CommandHudState
{
    public bool IsVisible { get; }
    public ToolId? ToolId { get; }
    public string? ToolName { get; }
    public string Prompt { get; }
    public IReadOnlyList<CommandOption> Options { get; }
    public IReadOnlyList<CommandHudField> Fields { get; }
    public string? Placeholder { get; }
}

public sealed class CommandHudField
{
    public string Key { get; }
    public string Label { get; }
    public double? LiveValue { get; }
    public string? Unit { get; }
    public bool IsEditable { get; }
}
```

Initial fields should be read-only. Direct editing belongs to HUD-7.

Exit criteria:

- The ViewModel can build a complete HUD state for the active command.
- Idle and selection visibility rules are explicit.
- Tool-specific field choices are centralized and testable.

### HUD-7 — Editable numeric HUD fields

Status: deferred until the read-only HUD and moved command input are stable.

This is intentionally separated because editing HUD fields creates new semantics that are not equivalent to submitting a single command-input string.

Scope:

- Add field focus/Tab traversal for distance, angle, width, height, radius or other numeric fields.
- Add a `CommandHudInputOverride` model for temporary typed values.
- Freeze live field values while the user is editing them.
- Convert field overrides into target points or scalar command inputs only when the current tool supports that behavior.
- Implement tool by tool, starting with Line.

Recommended order:

1. Line: Distance + Angle.
2. Rectangle: Width + Height.
3. Circle: Radius.
4. Polyline line mode: Distance + Angle.
5. Rect Sides.
6. Arc / Arc 3P.
7. Move / Copy / Mirror target phases.
8. Rotate / Scale / Offset / Fillet / Chamfer scalar phases.

Exit criteria:

- Editing numeric fields does not break the normal command input.
- `1000 Tab 45 Enter` style workflows work only where explicitly supported.
- Tools without supported field overrides keep read-only fields.

## Non-goals

- Do not rewrite the tool state machines only to support the HUD.
- Do not create duplicate command input boxes.
- Do not implement editable numeric HUD fields before the read-only HUD and moved command input are stable.
- Do not remove existing command-input tests; extend them.
- Do not make the HUD responsible for geometric decisions that belong in tools or input services.

## Implementation note — Step 3 read-only HUD overlay

Step 3 introduces the visual HUD as a read-only overlay. The purpose is to validate positioning, visibility, prompt display and live field display before any input behavior is moved.

Implemented behavior:

- The CAD canvas host contains an overlay `Canvas` above the drawing canvas.
- The HUD follows `HudScreenPosition` with a fixed offset.
- The HUD is clamped inside the canvas overlay bounds.
- The panel displays data from `CommandHudState` only.
- The old fixed command line remains active as the only command input.
- The overlay is not hit-test-visible and must not block the CAD canvas.

Deferred behavior:

- Moving the real `CommandInputTextBox` into the HUD.
- Editable numeric HUD fields.
- Tool-specific field customization beyond the initial generic live measurement fields.
- Removing the old bottom command line.

## Implementation note — Step 4 transitional command input in HUD

Step 4 introduces the command input textbox inside the HUD, but keeps a safe bottom fallback for states where the HUD is hidden.

Implemented behavior:

- The HUD panel contains `HudCommandInputTextBox` below prompt fields and options.
- The old bottom command row remains in the AXAML but is hidden while `IsCommandHudVisible` is true.
- The code-behind synchronizes the HUD textbox and the bottom textbox so they represent the same command input buffer.
- Existing command handling paths remain unchanged at ViewModel/tool level:
  - Enter submits through `SubmitCommandInput`;
  - Escape clears the current command text first, then cancels the active command;
  - Tab still performs command autocomplete when the command input has text;
  - Up/Down still navigate command history;
  - polyline keyboard shortcuts remain blocked when command input text is non-empty.

Rationale:

This is intentionally a transitional design. It validates the HUD as the visible command input for active command-driven tools without removing the idle fallback too early. The final removal of the bottom command row should happen only after idle command-entry UX is explicitly handled.

Deferred behavior:

- Editable numeric HUD fields.
- Removal of the bottom command row.
- Specialized input focus rules for every command phase.

## Implementation note — Step 5 HUD header icon polish

Step 5 keeps the transitional command-input architecture from Step 4, but replaces the temporary textual HUD marker with the real tool icon resources already used by the left toolbar.

Implemented in this step:

- The HUD header now contains `HudToolIcon` as a `Path` rather than the temporary `›` marker.
- `MainWindow.axaml.cs` resolves the current active tool display name to an existing icon resource key such as `IconLine`, `IconPolyline`, `IconRectangle`, `IconCircle`, `IconArc`, `IconMove`, `IconTrim`, `IconFillet`, `IconDistance` and related resources.
- The icon is refreshed together with HUD positioning, so tool changes update the HUD visual identity without changing the command contract.
- The bottom fallback row is intentionally still present for idle command entry.

Important constraints preserved:

- There are still no editable numeric HUD fields.
- The old command parser and `SubmitCommandInput` flow are unchanged.
- The old bottom row is still not deleted because idle command-entry discoverability is not yet replaced by a dedicated idle HUD.

Next recommended step: after icon rendering is confirmed manually, either add a compact idle HUD for typed commands or keep the bottom fallback until the final HUD removal milestone is designed safely.

## Implementation note — Step 6 bottom fallback demotion

Step 6 is a conservative consolidation step. It does not delete the bottom row yet, because idle command entry still needs a discoverable input surface while the cursor HUD is hidden. Instead, the bottom row is demoted from the active command prompt UI to a compact idle command launcher.

Implemented behavior:

- Active command prompt, options and live fields remain in the cursor HUD.
- The bottom fallback no longer shows the active tool name or prompt text.
- The bottom fallback shows only a `Command` label and the synchronized command input textbox.
- The fallback remains visible only when `IsBottomCommandLineVisible` is true, for example idle, selection-like states or before the HUD has a pointer position.
- Command submission, history, autocomplete, Escape and typed-character forwarding remain unchanged.

Why this step exists:

- It removes the last user-facing impression that the bottom row is still the primary command line.
- It keeps idle command entry safe until a dedicated idle HUD/launcher behavior is implemented.
- It avoids mixing the future editable numeric field work with command-line removal work.

Still deferred:

- Complete deletion of `BottomCommandLinePanel`.
- Dedicated idle floating command launcher.
- Editable numeric HUD fields.

## Implementation note — Step 7 contextual read-only HUD fields

Step 7 keeps the HUD read-only, but improves the field model so the values shown near the cursor match the active command phase more closely.

Implemented behavior:

- Generic two-point commands still show `Distance` and `Angle`.
- `Rectangle` now shows `Width` and `Height` while waiting for the opposite corner.
- `Rectangle Sides` now shows `Width`/`Angle` while defining the first side and `Height` while defining the second side.
- `Circle` now shows `Radius` while waiting for the radius point.
- `Arc` now shows `Radius`/`Angle` while defining the start point and `Angle` while defining the end direction.

Important constraints preserved:

- Fields are still display-only.
- No Tab navigation or numeric override model is introduced yet.
- Command parsing, history, autocomplete, Escape and tool state machines are unchanged.

Why this step matters:

- It validates that the HUD can adapt to command state without embedding command-specific UI logic in XAML.
- It prepares the future editable-field milestone with stable field keys such as `distance`, `angle`, `width`, `height` and `radius`.

## Implementation note — Step 8 extended contextual read-only fields

Step 8 extends the read-only field mapping to more command families while preserving the current command parser and tool state machines.

Additional mappings:

- `EllipseTool`
  - major axis phase: `Major radius`, `Angle`
  - minor radius phase: `Minor radius`
- `PolygonTool`
  - vertex/radius phase: `Radius`, `Angle`
- `RotateTool`
  - destination/angle phase: `Angle`
- `ScaleTool`
  - destination/factor phase: `Factor`
- `OffsetTool`
  - two-point distance phase: `Distance`
- `MirrorTool`
  - second mirror-axis point phase: `Distance`, `Angle`
- `BreakBetweenPointsTool`
  - second break point phase: `Distance`, `Angle`
- `MeasureAngleTool` and angular dimension phases: `Angle`
- radial dimension point-on-circle phase: `Radius`

A generic prompt-kind fallback now maps distance-like and angle-like `CommandInputKind` values to appropriate read-only HUD fields. This keeps the system extensible while avoiding XAML-specific command logic.

Still intentionally deferred:

- Editable numeric HUD fields.
- Geometry override model for typed `Distance`/`Angle`/`Width`/`Height`/`Radius` values.
- Bottom fallback removal.


## Implementation note — Step 9 generic option shortcuts

Step 9 improves command-option consistency without changing geometry, parser semantics or HUD numeric field behavior. Until now only a few commands, especially polyline, had direct key handling for option shortcuts while other commands required typing the option into the command input and pressing Enter.

Implemented behavior:

- When a command-driven tool exposes `CommandPromptState.Options`, pressing a matching shortcut key with an empty command input buffer submits that option immediately.
- The same logic is used whether focus is on the HUD command input, the fallback command input or the canvas/window.
- The shortcut is routed through the existing `SubmitCommandInput` path, so parsing, history, tool handling and status updates remain centralized.
- Existing special handling for polyline Enter completion and Align scale confirmation remains in place.

Examples:

- Polyline: `A`, `C`, `U`, `L` can be pressed directly when shown by the HUD.
- Fillet: `R` and `T` can be pressed directly when shown by the HUD.
- Trim: `A` and `U` can be pressed directly when shown by the HUD.
- Chamfer: `D` can be pressed directly when shown by the HUD.
- Spline: `C` and `U` can be pressed directly when shown by the HUD.

Important constraints preserved:

- Shortcuts are ignored when the command input already contains text, so normal typing/autocomplete remains safe.
- Only options actually exposed by the current `CommandPromptState` can be triggered.
- Numeric HUD fields remain read-only.
- The bottom fallback is still present.

## Implementation note — Step 10 editable-field metadata scaffold

Step 10 does not make the HUD numeric fields editable yet. It only strengthens the field model so the future override work has stable metadata and does not need to infer behavior from labels.

`CommandHudFieldViewModel` now exposes:

- `Kind`: `Distance`, `Angle`, `Width`, `Height`, `Radius`, `Factor` or `Generic`.
- `NumericValueText`: the numeric value without unit suffix.
- `DisplayValue`: the user-facing formatted value, including `°` for angles.
- `InputPlaceholder`: a stable short placeholder for future editable text boxes.
- `CanAcceptTypedOverride`: whether the field is a candidate for future typed override input.

The current XAML still renders fields through read-only text blocks. No Tab navigation, focus routing, parser changes or geometry override has been introduced in this step.

The next implementation step must introduce a real override model, for example `CommandHudInputOverride`, before any field is made editable. The first enabled workflow should remain limited to Line `Distance` + `Angle` so the behavior can be validated safely.

## Implementation note — Step 11 editable field input shell

Step 11 is the first UI-level editable-field step. It intentionally does not introduce the final geometric override model.

Behavior added:

- HUD fields are rendered as text boxes rather than static text.
- Enter inside a field submits the typed value through the same command input pipeline used by the HUD command input and the bottom fallback input.
- Escape restores the live value shown by the field and returns focus to the CAD canvas.
- Empty field text is restored on focus loss.
- HUD field text boxes are treated as input sources by `MainWindow`, preventing typed characters from also being appended to the command input buffer.

This is a conservative bridge step. It is useful for existing single numeric submissions such as distance/radius workflows, but it does not yet support combined typed overrides such as `Distance = 1000` plus `Angle = 45` before final confirmation.

Still intentionally deferred:

- `CommandHudInputOverride` state.
- Freeze/live override behavior while editing.
- Tab cycling with committed distance/angle pairs.
- Tool-specific preview override, beginning with Line.

## Implementation note — Step 12 Line one-shot field override

Step 12 introduces the first controlled geometry-aware HUD field submission. The scope is deliberately limited to `LineTool` in the `WaitingForSecondPoint` state.

Behavior:

- `Distance` field + Enter resolves the endpoint from the typed distance and the live cursor angle.
- `Angle` field + Enter resolves the endpoint from the live cursor distance and the typed angle.
- All unsupported tools, phases or fields fall back to the existing command input path.

This is not yet the full override model. No persistent field state is stored, no preview freeze is applied, and Tab-based combined editing remains deferred. This keeps the first geometry-aware step small and reversible.

## Implementation note — Step 13 Line persistent Distance/Angle override

Step 13 introduces the first persistent HUD override model. The scope is intentionally limited to `LineTool` in `WaitingForSecondPoint`.

The ViewModel stores distance and angle overrides independently. A non-empty field losing focus commits the value without confirming the line. Pressing Enter commits the value and confirms the endpoint. When both overrides are present, the endpoint is resolved from both values; otherwise the missing value comes from the live mouse measurement.

A new `CadWorkspace.PreviewPointFromCommandLine(...)` helper updates the active tool preview using a point that has already been resolved by the command/HUD layer. Like `SubmitPointFromCommandLine(...)`, it temporarily disables snapping, ortho and angle constraints to avoid applying input constraints twice.

Deferred by design:

- Rectangle width/height persistent override.
- Circle radius persistent override.
- Polyline line-mode Distance/Angle override.
- Arc and transform-tool overrides.
- Removal of the bottom fallback.

## Implementation note — Step 14 Polyline line-mode Distance/Angle override

Step 14 extends the persistent Distance/Angle HUD override model to `PolylineTool` while it is in `CollectingVertices`.

The supported active override targets are now:

```text
LineTool        WaitingForSecondPoint
PolylineTool    CollectingVertices
```

The same distance/angle point-resolution path is used for both. The resolved world point is sent to the active tool through the existing command-line pointer path:

- preview: `CadWorkspace.PreviewPointFromCommandLine(...)`;
- confirm: `CadWorkspace.SubmitPointFromCommandLine(...)`.

Polyline arc states are intentionally excluded from this override step. They continue to use the normal command input and pointer flow until a dedicated arc-field model is designed.


### Dynamic Command HUD mouse transparency update

The command HUD is now treated as a keyboard-driven overlay, not as a mouse target. The overlay is transparent to hit testing so fast mouse movement over `Distance`, `Angle` or the HUD command input cannot steal pointer events from the CAD canvas. Numeric HUD fields are entered from the keyboard using `Tab` from the command input, then `Tab` moves to the next numeric field and `Enter` confirms. This preserves the CAD rule that the mouse always remains free for picking points on the canvas.

## Step 16 — Compact polar/coordinate HUD without generic textbox

The command HUD direction has been revised: the generic visible textbox is removed and explicit numeric fields become the primary input surface.

Finalized UX direction for this step:

```text
TOOL NAME
Distance [123.45]  Angle [30.00]
X        [456.78]  Y     [120.00]
Line  Arc  Close
```

Option shortcuts are rendered by coloring only the shortcut character in yellow. Square brackets are no longer used.

Implementation decisions:

- Bottom command line row removed.
- Generic HUD textbox removed.
- Blue active command label removed with the bottom command row.
- Status bar no longer owns live pointer coordinates.
- HUD fields own coordinate display and numeric point input.
- Persistent state is represented by `CommandHudInputState` with `Distance`, `AngleDegrees`, `X`, and `Y`.
- Initial numeric typing is routed to the first editable HUD field.
- `Tab` cycles through fields: `Distance -> Angle -> X -> Y -> Distance`.
- The HUD remains mouse-transparent.

Scope:

- Full point override resolution is active for Line and Polyline line-mode.
- The model is generic, but additional tools still need command-specific semantics before all fields become final-editable.

## Step 17 — Numeric routing and first-point coordinate entry refinement

The compact HUD keeps coordinates visible, but automatic numeric routing must not treat `X` as the default field when a command has no base point yet.

Rules introduced:

- Automatic first-number routing chooses only primary measure fields: `Distance`, `Width`, `Radius`, or `Factor`.
- `X` and `Y` are keyboard-accessible through `Tab`, but are not the automatic destination for an initial number.
- When the active command is command-driven and expects point input, a complete `X`/`Y` pair resolves to an absolute UCS point and is submitted through the normal command-line point path.
- `Distance`/`Angle` remains a base-point dependent polar override and is currently enabled only for Line and Polyline straight-segment mode.

### Step 18 — Keyboard Tab focus trap

The compact HUD must own `Tab` navigation while it is visible. Avalonia's default focus traversal must not be allowed to move focus from the HUD/canvas to unrelated controls such as the right property panel during an active command.

Implementation notes:

- Use a tunneling key handler on `MainWindow` for `InputElement.KeyDownEvent`.
- Handle only plain `Tab` when the HUD is visible and the internal command input buffer is empty.
- If the source is a HUD field, commit the value with `confirm: false` and focus the next HUD field.
- If the source is the canvas or another non-HUD control, focus the first editable HUD field.
- Keep the HUD mouse-transparent; no pointer hit-testing should be re-enabled for the HUD fields.

Validation:

- Polyline first point: `Tab` focuses `X`.
- Polyline after first point: typing `100` fills `Distance`; `Tab` focuses `Angle`, not the property panel.

## Step 21 — Logical HUD input model

The first implementation based on real TextBox focus proved too fragile: `Tab` could remain on Distance or escape to the Property Panel, and temporary distance overrides could remain active across later polyline vertices. The HUD input model is now logical: code-behind tracks the active `CommandHudFieldKind` and a transient text buffer, while the HUD remains mouse-transparent. Pointer-confirmed points clear transient overrides so each new segment starts from live values unless the user types a new override.

## Step 22 — Active logical HUD field highlight and first-point coordinate entry

The HUD input state is now explicitly visible. Since the HUD remains mouse-transparent and no longer relies on real TextBox focus, the active field is highlighted by code-behind using the logical `CommandHudFieldKind`.

Rules:

- `Tab` selects the next available HUD field.
- The selected field receives a yellow border and darker active background.
- Plain numeric text is appended to the selected logical field buffer.
- For first-point phases, `Tab` starts coordinate entry at `X` and then `Y`.
- `Enter` with complete `X`/`Y` submits an absolute UCS point through the same command-line point path used by typed coordinates.
- Pointer hits are still ignored by the HUD; all mouse clicks remain canvas picks.

Manual checks:

```text
Line / Polyline first point:
Tab -> X highlighted -> type X -> Tab -> Y highlighted -> type Y -> Enter
```

```text
Line / Polyline after base point:
type distance -> Distance highlighted -> Tab -> Angle highlighted -> type angle -> Enter
```

## Step 23 — Active-field numeric routing correction

A review of the compact HUD implementation found that `GetDefaultLogicalHudFieldKindForNumericText()` preferred the default field before checking the current logical field. This could cause numeric input after `Tab` to return to `Distance` instead of staying on `Angle`.

Correct rule:

1. If the current logical HUD field is still available, route numeric text to it.
2. Otherwise choose the first preferred primary field (`Distance`, `Width`, `Radius`, `Factor`).
3. Do not automatically choose `X`; coordinate entry for first points is entered intentionally through `Tab`.

The shared HUD commit path also accepts `Width`, `Height`, `Radius` and `Factor` so the persistent HUD state can be extended tool by tool without adding another UI model.


### Step 24 — Freeze complementary polar HUD value

When the user starts typing a polar HUD value, the complementary live value is frozen immediately. Typing `Distance` freezes the current live `Angle`; typing `Angle` freezes the current live `Distance`. This prevents the preview update from recalculating the missing polar component from a changed/stale pointer state and keeps the value that was visible when typing began.

## Step 25-bis — Stabilization checkpoint after Rectangle rollback

This checkpoint freezes the currently stable HUD behavior before any further tool expansion.

Stable scope:

- The bottom command line and generic command textbox remain removed.
- The HUD remains mouse-transparent; all mouse picks belong to the CAD canvas.
- Line and Polyline straight-segment mode support logical HUD input through `Distance`, `Angle`, `X` and `Y`.
- First-point coordinate entry is intentional: `Tab -> X -> Tab -> Y -> Enter`.
- Plain numeric input during first-point prompts must not automatically route to `X`.
- After a base point exists, plain numeric input routes to `Distance` for Line/Polyline straight segments.
- `Tab` cycles logical HUD fields and must not move focus to the Property Panel.
- Typing `Distance` freezes the live `Angle`; typing `Angle` freezes the live `Distance`.
- HUD overrides are cleared after point confirmation so later polyline segments start from live values.

Non-goals for this checkpoint:

- Rectangle, Circle, Arc and Modify tools are not connected to editable HUD routing yet.
- The shared point override resolver must not be generalized for other tools without dedicated regression tests.
- No new command syntax is introduced.

Regression tests added in this checkpoint:
